## 1. Theming

### 1.1 Format decision (locked 2026-10-22)

**Mist defines its own generic theme format in the Material 3 semantic
vocabulary. It does not adopt any other application's format as its
native one.**

This is deliberately *not* "be Alacritty-compatible" and *not* "be
GTK-compatible". Those tie Mist's reader to one program's output and
break when that program changes. Instead Mist reads a vocabulary that
is published, neutral, and meaningful on its own.

The evidence for this choice is already on the user's machine.
Noctalia emits nine files from the same Material-You palette, and the
Hyprland one is the tell:

```lua
-- ~/.config/hypr/noctalia.lua  (generated by Noctalia)
local primary    = "rgb(eebf6d)"
local surface    = "rgb(17130b)"
local on_surface = "rgb(ece1d4)"
local secondary  = "rgb(dac3a1)"
local on_secondary = "rgb(3c2e16)"
local error      = "rgb(ffb4ab)"
local on_error   = "rgb(690005)"
…
        col = { active_border = primary, inactive_border = surface }
```

Material 3's role names — `primary`, `on_primary`, `surface`,
`on_surface`, `secondary`, `error` — are a real, documented colour
system, not one app's private vocabulary. Anything can emit them.

**Reader support.** Mist reads its native format first, then falls back
to importers for the formats Noctalia and others already produce, so
existing theme files work on day one:

| Format | Role | Status |
|--------|------|--------|
| **Mist native (Material 3 roles)** | canonical | **write this** |
| Alacritty TOML | importer | read-only |
| Ghostty (`palette = N=#rrggbb`) | importer | read-only |
| Kitty (`color0` … `color15`) | importer | read-only |
| KColorscheme JSON | importer | read-only |

Importers exist for convenience. The native format is what we document,
what we emit, and what we ask Noctalia (and others) to target.

### 1.2 Native format

```toml
# themes/my-theme.toml  — Mist native theme

[primary]
value = "#eebf6d"
on    = "#422c00"          # legible foreground on `primary`

[secondary]
value = "#dac3a1"
on    = "#3c2e16"

[tertiary]                 # optional
value = "#b4cea6"
on    = "#1a2a12"

[error]
value = "#ffb4ab"
on    = "#690005"

[success]
value = "#a6d96a"
on    = "#1e3d0f"

[warning]
value = "#eebf6d"
on    = "#422c00"

[surface]                  # the scrollback background
value = "#17130b"
on    = "#ece1d4"          # default text

[surface_alt]              # toolbar / status bar background
value = "#241f17"
on    = "#ece1d4"

[surface_raised]           # dialogs, panels, cards
value = "#2e2820"
on    = "#ece1d4"

[outline]                  # borders, separators, focus rings
value = "#4e4639"

[outline_variant]          # subtle dividers
value = "#2e2820"

[selection]
background = "#4e4639"
on         = "#d1c5b4"

[accent]                   # links, active tab, links hover
value = "#eebf6d"
on    = "#422c00"

[dim]                      # de-emphasised text: timestamps, hints
value = "#9a8f80"

# ANSI 16 — required. The world output pipeline is defined in terms of
# these indices, so a theme without them cannot render game text.
[ansi]
black   = "#4e4639"
red     = "#ffb4ab"
green   = "#a6d96a"
yellow  = "#eebf6d"
blue    = "#b4cea6"
magenta = "#dac3a1"
cyan    = "#8ec7c7"
white   = "#ece1d4"

# Optional: 256-colour cube approximation for 38;5;N under theme-priority.
# [ansi_ext]
# …
```

Every `value` also accepts the Material 3 reference syntax
(`{primary}`-style role references are out of scope for v1 — see open
questions).

**Minimal themes are legal.** A theme may specify only `[surface]`,
`[ansi]`, and nothing else; see §1.4 for derivation.

### 1.3 Built-in themes

Ship a set of well-known palettes, each expressed in the native
vocabulary:

- Dracula
- Catppuccin (Mocha, Macchiato, Frappé, Latte)
- Gruvbox (dark + light)
- Nord
- Solarized (dark + light)
- Tokyo Night, Tokyo Night Storm
- One Dark
- Rose Pine, Rose Pine Dawn
- Ayu (Mirage, Dark, Light)
- Kanagawa
- Material (Ocean, Palenight)
- A neutral default ("Wyldware")

Each built-in theme is a ~60-line TOML file compiled into the binary.

### 1.4 Derivation for omitted tokens

A minimal theme must still produce a coherent UI. Two categories:

**Semantic fallbacks** — token absent → fall back to the named ANSI
entry, then to a hard-coded default:

| Token | Falls back to |
|-------|---------------|
| `accent` | `ansi.yellow`, then `ansi.blue` |
| `accent.on` | `primary.on`, then `[surface].on` |
| `secondary` | `ansi.cyan`, then `ansi.magenta` |
| `error` | `ansi.red` |
| `success` | `ansi.green` |
| `warning` | `ansi.yellow` |
| `dim` | `mix(surface.on, surface.value, 0.45)` |
| `surface_alt` | `mix(surface.value, surface.on, 0.06)` |
| `surface_raised` | `mix(surface.value, surface.on, 0.12)` |

**Derivation, but authorable** — computed by default, overridable:

`outline`, `outline_variant`, and `selection.background`.

The user asked that **borders come from the theme**, and the survey
supports that: every app in the sample derives borders *from named
palette entries* rather than exposing a free-form border colour.

| App | Border treatment |
|-----|------------------|
| Kitty | `active_border_color = accent`, `inactive_border_color = palette[0]` |
| Hyprland (Noctalia) | `active_border = primary`, `inactive_border = surface` |
| GTK4 (Noctalia) | `sidebar_border_color = window_bg_color` — borders are invisible; the surface does the work |

So the rule is: **`outline` has a real value in the file, and if it is
absent we derive it as `mix(surface.value, surface.on, 0.20)`.** A theme
that wants invisible dividers sets `outline = surface.value`. A theme
that wants visible borders sets it to whatever it likes. Neither has to
know what a "mix" is.

This satisfies both halves of the requirement: the theme expresses border
intent, and a Noctalia-style minimal file still looks right.

### 1.5 Custom theme files and live reload

- A `themes/` directory next to the config, watched with the `notify`
  crate.
- The *active* theme file changing on disk → reparse and reapply within
  one frame. No restart, no menu trip.
- A new file appearing in the directory → appears in the picker without
  a restart.
- A malformed theme file → inline error in the picker, previous theme
  stays active. Never a crash.
- Picker shows file-backed and built-in themes in separate groups.
- File extension disambiguates: `*.toml` is native; other extensions
  route to the matching importer by sniffing content.

### 1.6 Theme precedence in the output pane

Two modes, per-world, with a global default:

- **`ansi-priority`** — the world's own colours win.
- **`theme-priority`** — the theme's palette is authoritative.

**Decision (locked 2026-10-22): truecolor always passes through, in
both modes.** Respecting the creator's design choice is the point; a
world that sends `#8a2be2` does so because that purple means something
to its players. Only *indexed* references get remapped, because an
index is a reference into a palette rather than a colour itself.

| World sends | `ansi-priority` | `theme-priority` |
|---|---|---|
| SGR `30`–`37` / `90`–`97` (indexed) | world's own palette at that index | **remap** into the theme's palette |
| SGR `38;5;N` (256-colour index) | cube entry N literally | **map** N to the theme's nearest entry |
| SGR `38;2;R;G;B` (truecolor) | `#RRGGBB` literally | `#RRGGBB` literally |

A `strict` sub-mode exists for anyone who wants every colour forced
through the theme, truecolor included: it clamps all three rows to the
theme's 256-colour approximation. Not the default.

**Chrome is always theme-owned** (locked 2026-10-22). Toolbar, status
bar, input line, tab strip, and side panels use theme tokens and never
world colours. A world that paints white-on-red must not make the
status bar unreadable.

## 2. Worlds and accounts

### 2.1 Two distinct concepts

The user named "a worlds list, and/or an accounts list" — these are
different things and the data model should keep them separate:

- **World** — a server endpoint. Name, host, port, plus per-world
  display and behaviour settings (theme mode, encoding, MCCP toggle,
  autosay, and so on).
- **Account** — a credential set against one or more worlds. Login,
  password, plus the character name if the server distinguishes it.

A world can have zero accounts (open telnet, no login) or several
(different characters). An account is scoped to a world; the same login
used on two worlds is two account records, because that's what the user
actually needs to manage.

### 2.2 Fields

**World**

| Field | Type | Notes |
|-------|------|-------|
| `name` | string | user-visible label, e.g. "Wyldware" |
| `host` | string | DNS name or IP |
| `port` | u16 | |
| `theme_mode` | enum | `ansi-priority` / `theme-priority` — per §1.4 |
| `theme` | string | optional per-world theme override |
| `encoding` | enum | `utf-8` (default) / `cp437` / `latin-1` |
| `autologin_account` | string? | which account to use automatically |
| `notes` | string? | free-form |

**Account**

| Field | Type | Notes |
|-------|------|-------|
| `world` | string | foreign key to `World.name` |
| `label` | string? | "Willow on Wyldware", "main alt", etc. |
| `login` | string | |
| `password` | string? | see §2.4 |
| `character` | string? | for MUSH-style post-login name selection |
| `autoconnect` | bool | connect without asking |

### 2.3 Login autodetection

The user wants the client to work out the login sequence itself based on
what the server presents. This is a real protocol-detection problem and
needs its own design.

Known login shapes in the MUD/MUSH/MOOWild ecosystem:

1. **Telnet IAC negotiation then a prompt** — server sends `login:` or
   `What is your name?` (case-insensitive, possibly ANSI-wrapped),
   possibly preceded by a banner.
2. **Line-by-line without a prompt** — server just wants input. Many
   old MUDs do this. Client types username, waits, types password.
3. **Password-only** — server prompts for a password only (some
   guest-able worlds).
4. **Post-connect character selection** — telnet login succeeds, then
   the MUSH asks "What is your name?" for the character. Penn/TinyMUSH
   `connect <name> <password>` or interactive prompt.
5. **MXP / secure-mode login** — the prompt is an MXP `<SEND>` link, so
   the string "login:" never appears literally.

Detection heuristic (first match wins, within a bounded window):

- Watch for a case-insensitive prompt match against a known set:
  `login`, `username`, `user name`, `name`, `what is your name`,
  `enter your name`, `account`, `ident`, `call`.
- Distinguish password prompts: `password`, `passphrase`, `pass:`.
- If no prompt appears within N seconds and N bytes, assume shape 2
  (unprompted) and send the login anyway.
- If MXP is active, parse `<SEND>` content as the prompt text too.

The matched prompt, and which account field it consumed, should be
recorded per world in the config as a learned hint, so the second
connection skips detection entirely. That satisfies "autodetect" without
making it a repeated cost.

**Decision (locked 2026-10-22): autodetection is opt-in, per world.**
A field in the world record:

```toml
[worlds.wyldware]
login_autodetect = false   # default for existing entries
```

Rationale: a wrong guess can send a password to the wrong prompt, and
some servers log failed logins. Opt-in puts the risk in the user's hands
where they can test it on a throwaway account first. The picker offers
"detect automatically" alongside "always use login X" so opting in is
one click.

### 2.4 Password storage

**Decision (locked 2026-10-22): OS keyring where available, obscured
plaintext as fallback.**

- Primary: the `keyring` crate — `secret-service` on Linux (GNOME
  Keyring, KWallet), Keychain on macOS, Credential Manager on Windows.
  The config stores an opaque handle like `keyring://wyldware/willow`.
- Fallback: if no keyring service is reachable (common on headless
  servers and minimal Linux installs), the password is written to the
  config **obscured, not encrypted** — a reversible transform so it's not
  sitting in plain sight in `cat config.toml`, but we do not claim it is
  secure. The UI says so explicitly: *"No system keyring available;
  password stored obscured in the config file. Do not share this file."*
- Never silently downgrade. The user is told which mode is in effect,
  every time, in the account editor.
- A `mist config paths` subcommand can print where credentials live so a
  user can check for themselves.

### 2.5 World list UI

The toolbar's current `Worlds` button is a placeholder. What it should
become:

- A side panel (not a modal — worlds are browsed while connected to one).
- Grouped by account if a world has more than one, otherwise flat.
- Each row: world name, host:port, last-connected timestamp, connection
  state indicator.
- Actions per row: connect, edit, duplicate, remove, set-as-default.
- Search/filter box when the list exceeds ~15 entries.
- Ordering: world records carry an integer `order` field. Manual
  reorder is available as **drag-to-reorder in the world picker**.

  **Effort estimate: low — roughly an hour.** The `order` field and a
  stable sort are part of the config work already planned in §2.2. The
  drag gesture itself is the only new UI, and egui's `egui_dnd` crate
  does the heavy lifting: ~40 lines to wrap each row in a draggable, a
  drop-target handler, and an order-rewrite on drop. No backend work
  beyond a `sort_order()` on the list. Worth doing when the list
  actually has an order worth maintaining, which it will for anyone
  running more than a handful of worlds.

## 3. Open questions

All seven original questions are settled. Three follow-ups remain:

1. **Material 3 role references.** The native format uses literal
   hex today. Should `value` also accept `{primary}`-style references to
   other roles (M3's dynamic-colour mechanism, so a theme can say
   "my accent *is* my primary")? Nice for hand-written themes, and it's
   how M3's own dynamic scheme works. Left out of v1 to keep the parser
   trivial.
2. **Noctalia `mist` template.** Making Mist a first-class Noctalia
   template target means contributing to Noctalia, not shipping anything
   ourselves. Worth doing eventually; it's a relationship to maintain.
3. **256-colour cube in the native format.** §1.2 sketches an optional
   `[ansi_ext]` table. The alternative is deriving all 240 non-ANSI
   entries from the 16 at load time, which every terminal does and which
   is usually indistinguishable in practice.

Nothing is blocked. §1.2's native format and §1.6's truecolor rule are
the two pieces of design worth a second read before we cut code.

## 4. Prioritisation suggestion

Roughly in dependency order, not importance order:

1. **Native theme format + token model + derivation (§1.2, §1.4)** —
   everything visual hangs off this. Nothing else in the UI can be
   finished until themes exist, because every colour decision depends
   on it.
2. **Theme importers (§1.1)** — Alacritty / Ghostty / Kitty /
   KColorscheme readers, so existing theme files work immediately.
3. **ANSI precedence rules (§1.6)** — the table that decides how a
   world's colour codes land. Needs §1 in place.
4. **Config schema for worlds and accounts (§2.2)** — data model first;
   the UI is a thin layer over it.
5. **Login autodetection (§2.3)** — self-contained, high user value,
   testable against `mist-mock` and then against wyldware.
6. **Built-in themes (§1.3)** — once the native format exists, each
   theme is ~60 lines of TOML. Can be parallelised.
7. **Password storage (§2.4)** — needs §2.2.
8. **World list UI (§2.5)** — needs §2.2.
9. **Live theme reload (§1.5)** — needs §1.2 and the `notify` dependency.
